Use case 60 · When something does not behave as expected

Help Index → When something does not behave as expected → Use case 60

Stop additional writes first, then distinguish an unwanted in-memory edit from an uncertain disk save. Protect the known-good backup before choosing a recovery path.

Before you start · Steps · Expected result · Saving · Check the result · Important details

Before you start

  1. Keep NMS closed. Record the exact error, loaded slot/context and any reported file paths; do not repeatedly retry Save.
  2. Keep the known-good backup unchanged. Resolve any unsynced Raw JSON first: leaving a tab with a red sync light asks Sync, Abandon or Cancel. Folder backups capture disk, not unsaved memory.
  3. A parse error or refused text stops with a message, keeps your text and keeps the light red; [] is applied on Bases, Starships and Teleport Endpoints and refused on Inventory by the count rule. Verify actual values. Inventory Raw JSON can be synced if it keeps the same inventories in the same order. Organizer and Replace Items from Backup remain the simpler tools for moves and replacement.

Steps

  1. Before syncing, formatting, retrying or reloading, preserve EACH pending Raw JSON pane externally. A parse error or refusal keeps the light red and your text unchanged; [] is applied on Bases, Starships and Teleport Endpoints and refused on Inventory by the count rule. If inventory replacement failed, capacity may already have expanded before missing Slots caused failure: inspect actual items/capacity, do not save or retry blindly, and deliberately reload the saved baseline if abandoning it. (control reference)
  2. If no live write was attempted and only app edits are unwanted, preserve other needed work and deliberately reload the intended disk slot. Read the replacement warning before accepting; reloading abandons unsaved app changes, not earlier disk writes. (control reference)
  3. If a live save failed, read whether recovery also failed. The writer attempts to restore the immediately pre-write data/meta pair after certain caught failures, but that is not a full backup or a guarantee against every interruption. Treat a recovery-failed warning as uncertain disk state. (control reference)
  4. For full-folder recovery, open Full Live Save Restore and read its Manual Instructions. Check the displayed runtime live directory and backup root, then identify your specific known-good backup. Copy Text only copies instructions; there is no restore execution button. (control reference)
  5. Before performing any manual replacement outside the app, preserve the current failed folder separately and verify both source and destination. The displayed destructive example removes live-directory contents. Stop if paths or backup contents are uncertain; do not run an example blindly. (control reference)
  6. After manual restore, reload the intended slot and inspect its context before editing. At the unsaved-close warning, Cancel keeps work open; Close discards it without saving. (control reference)

Expected result

  1. Recovery follows the identified failure scope while keeping the known-good backup separate from both failed disk files and unsaved editor text.

What changes, and when to save

Manual restore instructions neither restore nor save anything. Do not File → Save stale in-memory data over a restored folder; reload first. A new backup does not recover an earlier version automatically.

Check the result

  1. Confirm the reloaded slot/context and expected pre-edit values. Do not declare recovery from a copied command, closed dialog or success count alone.

Important details and recovery

  1. Never reuse the known-good backup as the destination for preserving a failed folder.
  2. The app has no universal undo-all. If recovery remains uncertain, keep NMS closed and retain all copies for diagnosis.
  3. When retaining understood text edits after a trustworthy baseline is restored, reapply them from external copies, sync and verify actual values.
