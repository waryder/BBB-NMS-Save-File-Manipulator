Use case 28 · Working with starships

Help Index → Working with starships → Use case 28

Review the upgrade field boundary before accepting the picker. The operation uses matched reference data, but non-Corvette equipment replacement is deliberately broader than adding a few missing modules.

Before you start · Steps · Expected result · Saving · Check the result · Important details

Before you start

  1. Make a full backup before replacing equipment you may want to keep.
  2. Load the correct context and sync or abandon any unsynced Raw JSON. If necessary, inspect the target’s current technology and cargo before starting.
  3. Only one tab can hold unsynced Raw JSON at a time: when you leave a tab whose sync light is red, the app asks Sync, Abandon or Cancel. Resolve that tab before structured operations, which refuse while any tab is unsynced.
  4. Before opening Upgrade Starships, record each intended zero-based ownership index in the tree. Named picker checkboxes show no visible index: count ALL ownership-ordered rows from one, including unoccupied rows; tree index 0 is picker row 1. Cancel if you cannot identify the row confidently.

Steps

  1. Keep a copy of complex edits you cannot afford to retype. Invalid or refused text is never applied: the error is shown, the text stays and the light stays red. Inventory Raw JSON must keep the same inventories in the same order.
  2. In Starships, inspect the intended ship’s Inventory, Inventory_TechOnly and Inventory_Cargo in Raw JSON or the expanded node tree. (control reference)
  3. Click Upgrade Starships and read the bold warning before checking a ship. (control reference)
  4. For a non-Corvette, decide whether replacing the entire technology Slots array with the matched reference’s complete item records is acceptable. Cancel if you need to protect the current equipment first. (control reference)
  5. If acceptable, count ALL ownership-ordered picker rows, including unoccupied rows, to select the preidentified ship slot. Cancel if uncertain; otherwise click OK and inspect the successful or skipped technology outcome. (control reference)

Expected result

  1. Validated base-stat lists are copied into general and technology inventories. General and cargo inventory class settings are set from the S-class reference. Successful technology processing targets a ten-by-six grid of sixty enabled cells.
  2. Identity, resource and seeds outside replaced technology records, appearance, linked builds, primary-ship selection and cargo contents/geometry are preserved. Supercharged-cell records are retained when compatible with the target grid.
  3. Corvettes use missing-only technology additions instead of wholesale equipment replacement.

What changes, and when to save

Changes stay in the loaded app data until File > Save NMS Save File writes the retained live slot and Main or Expedition context. Close No Man’s Sky and confirm that destination before saving; a green synchronization light alone does not mean the game file was saved. Compare the intended values before authorizing a live write.

Check the result

  1. For non-Corvettes compare the new technology layout with the reference-based result, not with an expectation that original extras survived.
  2. For a partial result check stats/class separately from unchanged technology items and capacity.

Important details and recovery

  1. Original technology extras, figurines, trails and module seeds can disappear on non-Corvettes. A malformed reference’s statistics or class causes whole-ship rejection; a technology-only failure does not cancel valid stats/class changes.
